### レビューのポイント

**ポイント1：お気に入りゾーン用の state を別に作らない（決めること A）**

第1版では `favoritedNote` という**別の state** を用意する案でした。その場合、

- ノート詳細の星 → **noteStore** の `isFavorite` を見る
- お気に入りゾーン → **favoritedNote** を見る

と、**同じ情報が2か所にある**ので、片方を更新し忘れると、星とゾーンがずれます。これが「2か所の連動」で一番起きやすいバグです。

**案**：noteStore だけを「本当の情報」にして、お気に入りゾーンは **`noteStore.getAll()` を `isFavorite` で `filter` したもの**にする（ゴミ箱の一覧のときの「ほかの値から計算できるものは state にしない」と同じ考え方）。こうすると、**どこでお気に入りを変えても、noteStore を1回更新するだけで、星とゾーンの両方が自動で変わる**。

**ポイント2：お気に入りを外すのは「ゴミ箱に入れるとき」か「復元するとき」の1か所に（決めること B）**

第1版では両方に書かれていました。**ゴミ箱に入れるときに外す**と、

- ゴミ箱に入っている間も「お気に入りではない」状態なので、お気に入りゾーンに出てこない
- 復元のときは何もしなくていい

と、処理が1か所で済みます。ゴミ箱の API（archive）は、すでに**子孫もまとめて**更新しているので、そこに `isFavorite: false` を足すだけです。

**ポイント3：リロードしたとき、子ノートのお気に入りが消える問題**

起動時（`fetchNotes`）に取得しているのは**一番上の階層のノートだけ**です。子ノートをお気に入りにしていても、▶ で開くまで noteStore に入っていないので、**リロードするとお気に入りゾーンから消えてしまいます**。
→ 起動時に「**お気に入りのノートの一覧**」も API から取得して、noteStore に入れる必要がある（ゴミ箱の `findTrash` と同じ形の API）。

**ポイント4：API の形（決めること D）**

| 案 | 例 | 特徴 |
| --- | --- | --- |
| 追加と解除を別にする | `PATCH /notes/:id/favorite`、`PATCH /notes/:id/unfavorite` | archive / restore と同じ形。わかりやすい |
| 切り替え（トグル）1つ | `PATCH /notes/:id/favorite`（今の逆にする） | API は1つ。ただし「今どっちか」を API に任せるので、連打したときに分かりにくい |
| 既存の更新 API を使う | `PATCH /notes/:id` に `{ isFavorite: true }` を送る | 新しいルートが不要。title / content と同じ扱い |

### 決めること

- **A**：お気に入りゾーンの state を別に作るか、noteStore から計算するか
- **B**：お気に入りを外すのは、ゴミ箱に入れるときか、復元するときか
- **C**：サイドバーの「…」メニュー：お気に入りのときは「お気に入りから外す」を出す？（本家は出さない＝ノート詳細からだけ外せる）
- **D**：API の形（上の3案）
- 列の名前：`isFavorite`（お気に入り？）と `isFavorited`（お気に入りにされた？）のどちらにするか。`isArchived` と並べると `isFavorite` の方が短く、よく使われる

### ✅ 決定（2026-10-26）

| | 決めたこと |
| --- | --- |
| A | お気に入りゾーンは、**noteStore を `isFavorite` で filter して作る**（別の state は作らない） |
| B | お気に入りを外すのは、**ゴミ箱に入れるとき**（archive API で自分と子孫の `isFavorite` を `false` に） |
| C | お気に入りのノートの「…」メニューには、**「お気に入りから外す」を出さない**（本家と同じ。外すのはノート詳細の星から） |
| D | API は**追加と解除を別にする**：`PATCH /notes/:id/favorite`、`PATCH /notes/:id/unfavorite` |
| 列名 | **`isFavorite`** |
