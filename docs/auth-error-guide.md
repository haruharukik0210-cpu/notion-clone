# 認証エラーを 500 → 401 にする（手順書）

## ゴール

ログインしていない・トークンが使えないときに、API が**正しい理由（401）**を返すようにする。フロントは 401 を受け取ったら、ログイン画面に戻す。

---

## 用語：HTTP ステータスコード

API が返事に付ける 3 けたの番号です。返事の中身を読まなくても、何が起きたかがわかります。

| 番号 | 意味 | EC サイトでたとえると |
| --- | --- | --- |
| 200 / 201 | 成功（201 は「作った」） | 注文できた |
| 400 | 送った内容がまちがっている | 住所の欄が空のまま注文した |
| **401** | **誰なのかわからない（ログインが必要）** | 会員ページを開いたら「ログインしてください」 |
| 403 | 誰かはわかるが、権限がない | ログインしているが、ほかの人の注文履歴は見られない |
| 404 | 見つからない | 削除された商品のページ |
| **500** | **サーバー側の故障** | お店のシステムが落ちている |

400 番台は「**送った側（フロント）の問題**」、500 番台は「**受けた側（サーバー）の問題**」です。

ログインしていないのに 500 を返すのは、「会員ページを開いたら『お店が故障しています』と出る」のと同じです。利用者も開発者も、原因を取りちがえてしまいます。

## 今の動き（捨てられる手元の DB で、実際に確かめた結果）

| # | 場面 | 今の返事 | 本来 |
| --- | --- | --- | --- |
| 1 | トークンなしで `GET /notes` | **500**（HTML のエラー画面） | 401 |
| 2 | 正しいトークンで `GET /notes` | 200 | 200 ✅ |
| 3 | 壊れたトークンで `GET /notes` | **500** | 401 |
| 4 | **壊れたトークンが残ったまま、ログインする** | **500（ログインできない）** | 200（ログインできる） |
| 5 | 壊れたトークンで `GET /auth/me` | **500** | 200（`null`＝未ログイン） |
| 6 | 削除されたユーザーのトークンで `GET /notes`（24 時間たって消えたゲストなど） | **500** | 401 |

### いちばん困るのは 4

フロントは、`localStorage` にトークンがあると、**どのリクエストにも**自動で付けて送ります（ログインのリクエストにも）。そのため、壊れたトークンが 1 つ残っていると、こうなります。

| 順番 | 起きること |
| --- | --- |
| 1 | アプリを開く → `/auth/me` が 500 → 待ち画面が「サーバーにつながりませんでした」になる |
| 2 | 「もう一度試す」を押しても、同じトークンを送るので、ずっと 500 |
| 3 | 利用者には直す方法がない（開発者ツールで `localStorage` を消すしかない） |

> **トークンが壊れるのはどんなとき？**：API の秘密鍵（`JWT_SECRET`）を変えたとき、トークンが書き換えられたとき、などです。今は起きていなくても、秘密鍵を変えた瞬間に、**ログインしていた全員**がこの状態になります。

## なぜ 500 になるのか

| 場所 | 今のコード | 何が起きるか |
| --- | --- | --- |
| `src/lib/auth.ts`（`Auth`） | `next(new Error('Unauthorized user'))` | エラーを Express に渡す → Express の**標準のエラー処理**は、何のエラーでも 500 と HTML を返す |
| `src/middleware/set-current-user.ts` | トークンが読めないと `throw new Error('Unauthorized')` | このミドルウェアは**全部のリクエスト**の前に動く → ログインも `/auth/me` も、全部 500 |

> **ミドルウェア**：リクエストが本来の処理（ルート）に届く前に、順番に通る関所です。`setCurrentUser` は「トークンから、誰なのかを調べる関所」、`Auth` は「ログインしていない人を通さない関所」です。
>
> **たとえ（PHP）**：WordPress の各ページの先頭で `if (!is_user_logged_in()) { … }` を書くのを、1 か所にまとめたものです。

## 方針

### API（AI が書く）

| # | 直すところ | どう直すか |
| --- | --- | --- |
| 1 | `Auth` | エラーを投げずに、`401` と `{ message: 'ログインが必要です' }` を返す |
| 2 | `setCurrentUser` | トークンが読めないときは、エラーにせず「**ログインしていない人**」として次へ進める |
| 3 | 最後のエラー処理（新しく足す） | それでも起きた想定外のエラーは、HTML ではなく JSON の 500 で返す。中身（スタックトレース）は外に出さない |

#### 2 で「すぐ 401 を返す」にしない理由

| | すぐ 401 を返す | ログインしていない人として進める（採用） |
| --- | --- | --- |
| 壊れたトークンでログイン | ❌ ログインも 401 になる（今と同じく、ログインできない） | ✅ ログインできる（新しいトークンで上書きされる） |
| 壊れたトークンで `/auth/me` | 401 | 200 で `null` → フロントはログイン画面へ |
| 壊れたトークンで `/notes` | 401 | `Auth` が 401 を返す（結果は同じ） |

「誰かを調べる関所」と「通さない関所」の**役割を分けたまま**にできるので、こちらを選びます。

### フロント（あなたが書く）

API が 401 を返すようになったら、フロントは**どの画面にいても**、401 を受け取ったらログイン画面に戻します。

1 か所にまとめて書けるのが、axios の**レスポンスのインターセプター**です。今あるのは「送る前に割り込む」リクエストのインターセプターで、トークンを付けています。今回は「**返事を受け取った直後に割り込む**」ほうを足します。

| 種類 | いつ動く | 今あるもの・作るもの |
| --- | --- | --- |
| リクエストのインターセプター | 送る直前 | トークンを付ける（`request.ts`）✅ |
| レスポンスのインターセプター | 返事を受け取った直後 | 401 ならログイン画面へ（**今回作る**） |

## シナリオ表（あなたが埋める）

API を直したあとの、フロントの動きを決めます。

| # | 場面 | API の返事 | あなたの答え | 決めたこと |
| --- | --- | --- | --- | --- |
| 1 | 壊れたトークンが残った状態で、アプリを開く | `/auth/me` → 200（`null`） | ログイン画面に遷移 | ✅ 今のフロントのままで、そうなる（Layout が「ユーザーなし → `/signin`」にする）。インターセプターは関係しない |
| 2 | 1 のあと、ログインする | `/auth/signin` → 200 | ログインでき、ホームに遷移 | ✅ 新しいトークンで上書きされるので、壊れたトークンも消える |
| 3 | 24 時間たってゲストが消えた。開いたままのタブでノートを作る | `POST /notes` → 401 | ログイン画面に遷移 | ✅ **インターセプターの出番**。ログイン画面に移す前に、使えなくなったトークンも消しておく（残しておく意味がないため） |
| 4 | サーバーの故障で、ノートの読み込みに失敗 | `GET /notes` → 500 | 「サーバーにつながりませんでした」等のエラー | ✅ インターセプターは**何もしない**（エラーをそのまま呼び出し元に返す）。今は呼び出し元の `alert` が出る。画面上のエラー表示は、リスト 8「読み込み中・空・エラーの表示」でやる |
| 5 | ログイン画面でパスワードをまちがえた | `/auth/signin` → **401** | 手直しなし（今の動きが正しい） | ✅ そのとおり。ということは、インターセプターは「**401 なら、いつでもログイン画面へ**」ではいけない。ログインのリクエストの 401 は、**よけて**通す必要がある |

### 5 からわかること

同じ 401 でも、意味が 2 つあります。

| | 3：ノートを作る | 5：ログインする |
| --- | --- | --- |
| 401 の意味 | 「あなたが誰か、もうわからない」 | 「メールかパスワードがちがう」 |
| してほしいこと | ログイン画面へ | その場で「ログインに失敗しました」 |

インターセプターは、この 2 つを見分ける必要があります。

## 手順

### Step 1：シナリオ表を埋める

上の表を埋めてください。

### Step 2：API を直す（AI）

ブランチは API のリポジトリで作ります。

1. **API の開発サーバーを止める**（ターミナルで `Ctrl + C`）。ファイルを書き換えると自動で再起動し、`.env` の DB につながってしまうため
2. Sourcetree で **notion-clone-api-postgres** を開く → `master` をプル → `fix/auth-401` というブランチを作る

ブランチができたら教えてください。AI が直して、捨てられる手元の DB で「今の動き」の表の 6 つを確かめます。

> **API を先に出しても大丈夫か**：大丈夫です。今のフロントは、401 でも 500 でも「失敗」として同じように扱うので、壊れません。`/auth/me` は 500 から `null` に変わるので、むしろ 4 の「ログインできない」が先に直ります。

### Step 3：フロントのインターセプターを書く（あなた）

#### 書く場所

`src/lib/api/` の中です。リクエストのインターセプター（`request.ts`）と同じように、ファイルを分けて作り、`src/lib/api/index.ts` で登録します。

#### あなたが書くこと

| # | やること | ヒント |
| --- | --- | --- |
| 1 | レスポンスのインターセプターを登録する | `api.interceptors.response.use(成功したとき, 失敗したとき)`。成功したときは、何もせずにそのまま返す |
| 2 | 401 かどうかを調べる | 失敗したときの関数は、axios のエラーを受け取る。返事の番号は `error.response?.status` に入っている（通信そのものが失敗したときは `response` がないので `?.`） |
| 3 | ログインのリクエストはよける（シナリオ 5） | どのリクエストの返事かは `error.config` に入っている。どれを見れば「ログインのリクエストか」がわかる？ ほかに、よけたほうがいいリクエストはない？ |
| 4 | 401 のとき | トークンを消す → ログイン画面へ |
| 5 | エラーを呼び出し元に返す | 最後に `return Promise.reject(error)`。これを忘れると、呼び出し元の `catch` が動かず、「成功した」扱いになってしまう |

#### 4 の「ログイン画面へ」の方法

インターセプターは React の部品ではないので、`useNavigate` は使えません（フックは部品の中でしか使えないため）。

| 方法 | 動き | 向いているか |
| --- | --- | --- |
| `window.location.href = "/signin"` | ページを読み込み直して移動 | ✅ 読み込み直すので、atom に残った古いユーザー情報も一緒に消える。今回はこれで十分 |
| `useNavigate` | ページを読み込み直さずに移動 | ❌ インターセプターの中では使えない |

> **たとえ（PHP）**：`header('Location: /signin.php'); exit;` と同じです。

#### 流れ（シナリオ 3）

| 順番 | どこで | 起きること |
| --- | --- | --- |
| 1 | SideBar | ＋を押す → `noteRepository.create()` |
| 2 | API | 401 を返す |
| 3 | **インターセプター** | 401、かつログインのリクエストではない → トークンを消す → `/signin` へ移動 → エラーを返す |
| 4 | SideBar の `catch` | `alert` が出る（移動の直前に一瞬）※ 気になれば、あとで直す |
| 5 | ログイン画面 | 読み込み直したので、ログイン画面が出る |

- 本番で、開発者ツールの `localStorage` の `token` をわざと書き換えて、ログイン画面に戻ること・ログインし直せることを見る
