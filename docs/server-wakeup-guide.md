# サーバーを起こしている表示（手順書）

## ゴール

API のサーバーが休止しているときに、デモの URL を開いても、**「壊れている」と思われずに待ってもらえる**ようにする。

採用担当の人が README からデモを開いたとき、最初に見る画面です。ここで真っ白なまま 1 分待たせると、中身を見てもらう前に閉じられてしまうかもしれません。

---

## 今の動き（調べた結果）

| 順番 | どこで | 何が起きるか |
| --- | --- | --- |
| 1 | `App.tsx` | `isLoading` が true のあいだ、`return <div />`（**真っ白**） |
| 2 | `App.tsx` の `useEffect` | `GET /auth/me` を呼ぶ。ログインしていない人も呼ぶ |
| 3 | Render | 休止中なら、サーバーが起きるまで **30〜60 秒**かかってから返事が来る |
| 4 | `App.tsx` | 返事が来たら `isLoading` を false にして、画面を出す |

つまり、**休止中に開くと、誰でも 30〜60 秒は真っ白**です。何も出ないので、読み込み中なのか壊れているのか区別できません。

> **たとえ**：EC サイトで「注文する」を押したあと、ボタンも画面も何も変わらない状態です。お客さんは、もう一度押すか、ページを閉じてしまいます。

## 方針の比較

| 案 | 内容 | 良いところ | 気になるところ |
| --- | --- | --- | --- |
| A | 待っているあいだ、すぐ「読み込み中」を出す | かんたん | サーバーが起きているとき（0.3 秒くらい）にも一瞬だけ出て、**ちらつく** |
| **B（採用）** | **数秒たっても終わらないときだけ**、「サーバーを起動しています。1 分ほどかかることがあります」と出す | 普段はちらつかない。長いときだけ、理由と目安を伝えられる | タイマーの扱い（止める・片付ける）が必要 |
| C | 進み具合のバー（○○%） | 見た目がわかりやすい | 本当の進み具合はわからないので、**うその表示**になる |
| D | サーバーを休止させない（外から定期的にアクセスする・有料プラン） | 待ち時間そのものがなくなる | 無料プランの使い方として不自然。今回はしない |

B を選ぶ理由は、**「待たせる理由」と「どのくらい待つか」を伝えられる**からです。待つ時間が同じでも、理由と目安がわかると、人は待てます。

> **用語メモ**
> - **ちらつき（flash）**：一瞬だけ表示が出てすぐ消えること。かえって落ち着かない印象になります
> - **遅延表示**：決めた時間が過ぎてから表示すること。今回の B です

## どこで待つか

| 場所 | 休止中の待ち時間 | 今回やるか |
| --- | --- | --- |
| **アプリを開いたとき**（`App.tsx` の `/auth/me`） | 30〜60 秒 | **やる**（ここがいちばん大事） |
| ログイン・ゲストのボタン | 開いたときにサーバーが起きるので、ふだんは短い | 今のまま（「準備中」が出る） |
| ログインしたあとのノートの読み込み（`Layout.tsx`） | サーバーはもう起きているので短い | 今回はしない（リストの 8「読み込み中・空・エラーの表示」でやる） |

アプリを開いたときに `/auth/me` を呼ぶので、そこでサーバーが起きます。そのあとの通信は速くなります。なので、**最初の 1 か所を直せば、ほとんどの場面がカバーできます**。

## シナリオ表（あなたが埋める）

本家の Notion を観察したときと同じように、「こうなってほしい」を先に決めます。前提は「何秒たったら文言を出すか」の時間で、ここでは **3 秒**とします（変えても大丈夫です）。

| # | 場面 | あなたの答え | 決めたこと |
| --- | --- | --- | --- |
| 1 | サーバーが起きているときに開く。0.3 秒で返事が来る | アプリを表示 | ✅ そのとおり。文言は一度も出さない |
| 2 | 休止中に開く。0〜3 秒のあいだ | アプリを表示 | ⚠️ **まだ返事が来ていないので、アプリは出せない**（ログインしているかどうかも、まだわからない）。文言のない、静かな待ち画面にする |
| 3 | 休止中に開く。3 秒たっても返事がない | 「サーバーを起動しています。1 分ほどかかることがあります」 | ✅ そのとおり |
| 4 | 3 のあと、40 秒で返事が来た | アプリを表示 | ✅ そのとおり。ログインしていなければログイン画面、していればノート |
| 5 | 3 のあと、返事がエラーだった | サーバーが落ちている・ネットがつながらない等の表示 | ✅ 方向はそのとおり。ただし、フロントからは「サーバーが落ちている」のか「ネットがつながらない」のかを**見分けられない**（どちらも「返事が来なかった」になる）。なので、1 つの文言にまとめて、両方の可能性と「もう一度試す」ボタンを出す |
| 6 | 0.3 秒で返事が来たあとの、3 秒のタイマー | 止まってリセットされるべき | ✅ **止める（取り消す）**が正解。止めないと、3 秒後に「遅い」の状態に変わってしまう。待ち画面はもう消えているので、今は害がない。でも「アプリが表示されているのに、state は『遅い』」という**うその状態**が残る。リセット（もう一度 0 から数える）までは不要 |

### 2 について：「待ち画面」と「文言」は別のもの

| 時間 | 画面 | 文言 |
| --- | --- | --- |
| 0〜0.5 秒 | 真っ白（背景色だけ） | なし |
| 0.5〜3 秒 | くるくる回る印だけ | なし |
| 3 秒〜 | くるくる回る印 | 「サーバーを起動しています」 |

0.5 秒までは、CSS で印も隠しています。すぐ返事が来たとき（1 の場面）に、何もちらつかないようにするためです。この 0.5 秒は CSS（`animation-delay`）だけで実現しているので、ロジックはいりません。

### 0.5 秒は CSS、3 秒は JS で分ける理由

| | 0.5 秒（印を出す） | 3 秒（文言を出す） |
| --- | --- | --- |
| 変わるもの | 見た目だけ（透明 → 見える） | **出す内容**（文言が増える） |
| 担当 | CSS（`opacity: 0` から、0.5 秒後にフェードイン） | JS（state を変えて、文言を表示する） |
| CSS だけでもできる？ | できる（今そうしている） | 見た目だけならできる。でも、透明にしただけの文字は**画面読み上げソフトには最初から読まれてしまう**。すぐ返事が来たときにも「サーバーを起動しています」と読み上げられる |
| エラーとの関係 | なし | エラーは「返事が失敗した」という JS でしかわからない情報。3 秒も同じ state で管理すると、状態がまとまる |

### タイマーと `/auth/me` は同時に動く

「3 秒待ってから `/auth/me` を呼ぶ」のではありません。**0 秒の時点で両方とも始まります**。

| 時間 | `/auth/me`（返事を待つ） | 3 秒のタイマー（文言を出すかを決める） |
| --- | --- | --- |
| 0 秒 | 呼ぶ（返事を待ち始める） | 予約する |
| 3 秒 | まだ待っている | 鳴る → 文言を出す |
| 40 秒 | 返事が来る → アプリを表示 | （もう鳴ったあと） |

`setTimeout` は「3 秒後にこれをやって」と**予約するだけ**で、その場で 3 秒止まるわけではありません。予約したら、すぐ次の行（`/auth/me` を呼ぶ）に進みます。

> **たとえ**：電子レンジのタイマーをセットしてから、待たずに洗い物を始めるのと同じです。タイマーが鳴るまで、ほかの作業は止まりません。

## 手順

### Step 1：ブランチを作って、シナリオ表を埋める

Sourcetree で次の順に操作します。

1. 左の「ブランチ」で `master` をダブルクリックして、`master` に切り替える
2. 上の「プル」を押す → PR #12（ゲストログイン）が手元の `master` に入る
3. 上の「ブランチ」を押す → 新しいブランチ名に `feat/server-wakeup` と入れて、「ブランチを作成」

> **なぜ先にプルするのか**：手元の `master` は、まだ PR #12 をマージする前の状態です。古い `master` からブランチを作ると、ゲストログインが入っていない状態から始まってしまいます。

ブランチを作ったら、上のシナリオ表を埋めてください。

### Step 2：待ち画面の見た目を作る（AI）✅

| ファイル | 内容 |
| --- | --- |
| `src/components/StartupScreen.tsx` | 待ち画面の部品。`status` で見た目を切り替える。時間の判断はしない（`GuestBanner` と同じく、見た目だけ） |
| `src/styles/components/startup-screen.css` | 画面の真ん中に出す。くるくる回る印は 0.5 秒たってから出す。動きを減らす設定の人には、回転を止める |
| `src/index.css` | 上の CSS を読み込む |

> この機能だけは、props と型も AI が書いています（本来はあなたが決める部分。次の機能からは、AI は見た目だけ）。

部品の使い方：

```tsx
<StartupScreen status="waiting" />                 // 文言なし（印だけ）
<StartupScreen status="slow" />                    // 「サーバーを起動しています」
<StartupScreen status="error" onRetry={…} />       // 「サーバーにつながりませんでした」＋「もう一度試す」
```

`StartupStatus` は `"waiting" | "slow" | "error"` の 3 つの文字列だけを受け付ける型です（**ユニオン型**）。`"slw"` のように書きまちがえると、型チェックで気づけます。

> **なぜ boolean を 2 つ（`isSlow`・`isError`）にしなかったのか**：boolean が 2 つだと「遅い、かつエラー」という、ありえない組み合わせも作れてしまいます。状態を 1 つの値にまとめると、**ありえない状態を、そもそも作れなく**なります。

### Step 3：ロジックを書く（あなた）

#### App.tsx のロジック

今の `isLoading` と `return <div />` を置きかえます。

| # | やること | ヒント |
| --- | --- | --- |
| 1 | 状態を持つ | 「待っている／遅い／エラー／もう表示してよい」を、どんな state で持つか。`StartupStatus` を import して使うと、部品と型がそろう |
| 2 | 3 秒のタイマーを予約する | `/auth/me` を呼ぶ**今の `useEffect` の中**で `setTimeout`。新しい `useEffect` を作ると、`/auth/me` の成功・失敗とつなげにくい |
| 3 | 返事が来たら、タイマーを取り消す | `setTimeout` は**タイマーの番号**を返す。その番号を `clearTimeout` に渡すと取り消せる。成功しても失敗しても取り消したい → `try` / `catch` / `finally` のどこに書く？ |
| 4 | エラーのとき | `catch` の中で |
| 5 | 片付け（クリーンアップ） | `useEffect` の最後で `return () => { … }` を書くと、コンポーネントが消えるときに呼ばれる。ここでもタイマーを取り消す |
| 6 | 「もう一度試す」 | いちばんかんたんなのは、ページの再読み込み（`window.location.reload()`） |
| 7 | 表示を切り替える | 「まだ表示しない」あいだは、`<BrowserRouter>` の代わりに StartupScreen **だけ**を返す。`<BrowserRouter>` の中に一緒に置くと、アプリと待ち画面が両方出てしまう |

#### 流れ（休止中に開いた場合）

| 時間 | 起きること | state |
| --- | --- | --- |
| 0 秒 | `useEffect` が動く → 3 秒のタイマーを予約し、**同時に** `/auth/me` を呼ぶ | 待っている |
| 3 秒 | タイマーが鳴る → 「遅い」にする | 遅い |
| 40 秒 | 返事が来る → タイマーを取り消す（もう鳴ったあとなので、何も起きない）→ ユーザーを保存 | 表示してよい |

#### 流れ（起きているときに開いた場合）

| 時間 | 起きること | state |
| --- | --- | --- |
| 0 秒 | 3 秒のタイマーを予約し、**同時に** `/auth/me` を呼ぶ | 待っている |
| 0.3 秒 | 返事が来る → **タイマーを取り消す** → ユーザーを保存 | 表示してよい |
| 3 秒 | （取り消したので、何も起きない） | 表示してよい のまま |

> **たとえ**：JS の `setTimeout` は、キッチンタイマーのようなものです。料理が早くできたら、鳴る前にタイマーを止めます。止め忘れると、食べ終わったあとに「できました！」と鳴ってしまいます。

#### 5 の片付けが必要な理由

開発中は `StrictMode` のせいで、`useEffect` が**わざと 2 回**動きます（片付け忘れを見つけるための、React の仕組みです）。片付けがないと、タイマーが 2 つ予約されてしまいます。片付けを書くと、1 回目のタイマーは取り消されます。

> **たとえ**：PHP にはないけれど、JS で `addEventListener` をしたら、いらなくなったときに `removeEventListener` するのと同じ考え方です。

- E2E を書くかどうかは、Step 3 のあとに決める
