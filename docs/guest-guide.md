# お試しアカウント（ゲストログイン）手順書

採用担当者が、**登録なしでボタン1つで触れる**ようにします。

## ゴール

```
ログイン画面
┌──────────────────────┐
│ メールアドレス [        ] │
│ パスワード     [        ] │
│ [ ログイン ]               │
│ ──────── または ──────── │
│ [ ゲストで試す ]           │  ← 押すと、すぐサイドバーにサンプルのノートが並ぶ
└──────────────────────┘
```

- 押したら、**登録なし**でログインできる
- **サンプルのノート**（子ノートつき）が最初から入っている。並び替えや子ノートをすぐ試せる
- ほかの人の操作で、**自分のノートが消えたり書き換わったりしない**

---

## 決めること：どう作るか

| 方法 | 中身 | よいところ | 困るところ |
| --- | --- | --- | --- |
| A. 共有のゲストアカウント | `guest@example.com` / `password` を README に書いておき、全員が同じアカウントを使う | 作るのが一番かんたん（API の変更なし） | **全員が同じノートを見る**。前の人が全部消したり、変な言葉を書いたりすると、次の人もそれを見る |
| **B. 押すたびに、使い捨てのゲストを作る** ← おすすめ | ボタンを押すと、API がその人専用のゲストを作り、サンプルのノートを入れて返す | 人ごとに分かれているので、**ほかの人の影響を受けない**。いつ開いても、きれいな状態から始まる | API に新しい仕組みが必要。ゲストが増え続けないように、古いゲストを消す仕組みもいる |

→ **B がおすすめ**です。採用担当者は「突然開く」ので、いつでもきれいな状態で見せられることが大事です。設計の話としても、面接で話せる内容が増えます。

**たとえ**：B は、EC サイトの「ゲスト購入」に近いです。会員登録なしで、その場限りのカートを作ります。

## 全体の設計（B の場合）

### 流れ

```
① 「ゲストで試す」を押す
② フロントが API に POST /auth/guest を送る
③ API：24時間より前に作られたゲストを削除する（ノートも一緒に消える）
④ API：新しいゲストのユーザーを作る（メールアドレスとパスワードは、ランダムに作る）
⑤ API：そのゲストに、サンプルのノートを作る
⑥ API：ログインと同じ形 { user, token } を返す
⑦ フロント：ログインと同じように、user を保存して token を localStorage に入れる → トップへ
```

### ① DB：ユーザーに「ゲストかどうか」の印を付ける

| 列 | 型 | 中身 |
| --- | --- | --- |
| `isGuest` | boolean | ゲストなら true。ふつうのユーザーは false（初期値） |

**なぜ列を足すのか**：③で「古いゲストだけ」を消すときに、ゲストと本物のユーザーをはっきり見分けるためです。メールアドレスの形（`@guest.local` で終わる、など）で見分けることもできますが、もし同じ形で登録した人がいたら、その人まで消してしまいます。

### ② API：`POST /auth/guest`

| 処理 | 中身 |
| --- | --- |
| 古いゲストを消す | `isGuest = true` かつ、作られてから 24 時間より前のユーザーを削除。ノートは `ON DELETE CASCADE` で一緒に消える |
| ゲストを作る | 名前「ゲスト」、メールアドレス `guest-（ランダムな文字列）@guest.local`、パスワードもランダム（誰も知らない） |
| サンプルのノート | 下の表のノートを作る（`position` も付ける） |
| 返すもの | `{ user, token }`（`/auth/signin` と同じ形。フロントの処理を共通にできる） |

**サンプルのノート（案）**

```
📘 はじめに（このアプリでできること）
📝 買い物メモ
📂 読書記録
   ├ 📗 読みたい本
   └ 📙 読み終わった本
```

**別の消し方（cron）との比較**

| 消すタイミング | よいところ | 困るところ |
| --- | --- | --- |
| **ゲストを作るたびに消す** ← おすすめ | 仕組みが1つで済む。無料プランでも動く | 誰もゲストを作らないあいだは、古いゲストが残る（でも、増えもしない） |
| 毎日決まった時間に消す（cron） | 時間どおりに消える | 定期実行の仕組みが別に必要。Render の無料プランでは使えない |

**cron（クーロン）とは**：決まった時間に処理を自動で動かす仕組みです。

### ③ フロント

| 変更 | 中身 |
| --- | --- |
| `authRepository.guest()` | `POST /auth/guest` を送って、`{ user, token }` を返す（`signin` とほぼ同じ） |
| ログイン画面の「ゲストで試す」ボタン | 押したら `guest()` → ログインと同じ処理 |
| ゲストで使っているときの表示 | 「ゲストとして利用中です。データは 24 時間で消えます」（サイドバーの上など） |

## 気をつけること（セキュリティ）

| 心配なこと | 対策 |
| --- | --- |
| ボタンを連打されて、ゲストが大量に作られる | 同じ IP からの回数を制限する（`express-rate-limit`。例：1時間に 10 回まで） |
| 消したゲストのトークンが残る | トークンのユーザーが見つからなければ、API は「未ログイン」として扱う。今の作り（`set-current-user.ts`）のままで大丈夫 |
| 本物のユーザーを消してしまう | `isGuest = true` のユーザーだけを消す。**ここは使い捨ての DB でテストしてから**本番に出す |

**IP（アイピー）とは**：インターネット上の住所のような番号です。同じ住所から何度も来たら止める、という使い方をします。

| # | 操作 | 期待する結果 |
| --- | --- | --- |
| 1 | ログイン画面で「ゲストで試す」を押す | トップに移動して、サイドバーにサンプルのノートが並ぶ |
| 2 | ゲストのまま、ページを再読み込みする | 内容はそのまま（トークンが localStorage に残っている） |
| 3 | ゲストでノートを1つ消してから、ログアウトする。もう一度「ゲストで試す」を押す | **新しいゲスト**になり、サンプルのノートが全部そろった状態から始まる（消したノートも元どおり） |
| 4 | 2人が同時にゲストで使う | 1人ずつ別のゲストなので、ぶつからない（B を選んだ理由そのもの。追加の対策はいらない） |
| 5 | ゲストを作ってから 25 時間後に、そのままページを開く | まだ誰も新しいゲストを作っていなければ、**そのまま使える**。消されていれば、**ログイン画面に移る**（`/auth/me` が `null` → `Layout` が `/signin` へ） |
| 6 | 「ゲストで試す」を押して、API の返事を待っているあいだ | ボタンを**押せなくして**（`disabled`）、文言を「準備中…」にする。ログインボタンも押せなくする |
| 7 | API がエラーを返した | `alert` で知らせる。回数制限（429）のときは、API の文言「しばらく時間をおいてから…」を出せるとよりよい |

**わかったこと**：ゲストでログアウトすると、トークンが消えます。パスワードは誰も知らないので、**そのゲストには二度と入れません**。

#### ① マイグレーション

```sql
ALTER TABLE "user" ADD "isGuest" boolean NOT NULL DEFAULT false
```

今いるユーザーは全員 `false`（ゲストではない）になります。`DEFAULT false` があるので、今の新規登録（`/auth/signup`）は何も変えなくても `false` で作られます。

#### ② `POST /auth/guest` の流れ

```ts
const user = await datasource.transaction(async (manager) => {
  // ① 24 時間より前のゲストを削除（isGuest = true だけ。ノートは CASCADE で一緒に消える）
  await manager.delete(User, { isGuest: true, createdAt: LessThan(24時間前) });
  // ② ゲストを作る（メールもパスワードもランダム）
  const guest = await manager.save(User, { name: 'ゲスト', email: `guest-${randomUUID()}@guest.local`, ... });
  // ③ サンプルのノートを入れる
  await createSampleNotes(manager, guest.id, guestSampleNotes, null);
  return guest;
});
// ④ ログインと同じ形 { user, token } で返す
```

| 書き方 | 意味 |
| --- | --- |
| `datasource.transaction(...)` | ①〜③を「全部成功」か「全部なかったこと」にする。ゲストだけできて、ノートが半分しかない、を防ぐ |
| `LessThan(日時)` | TypeORM の書き方で、SQL の `createdAt < 日時` |
| `randomUUID()` | Node.js に入っている、毎回ちがうランダムな文字列を作る関数 |
| `createSampleNotes` | 親のノートを作って、その id を `parentId` にして子のノートを作る。**自分で自分を呼ぶ**（再帰）ので、何階層でも作れる。NoteList が子の NoteList を呼ぶのと同じ形 |
| `position: index` | 同じ親の中で 0, 1, 2 … と振る（並び替えがすぐ試せる） |

#### ③ サンプルのノートの中身

エディタ（BlockNote）が保存する形と同じ「ブロックの配列」を JSON にして、`content` に入れています。

```ts
{ type: 'bulletListItem', content: 'サイドバーの ⋮⋮ をつかんで、ノートを並び替える' }
```

#### ④ 回数の制限

| 設定 | 値 |
| --- | --- |
| 数える単位 | アクセスした人の IP ごと |
| 上限 | 1 時間に 10 回。こえたら **429**（Too Many Requests）と「しばらく時間をおいてから…」 |

**`trust proxy` とは**：Render では、リクエストが一度 Render の中継サーバー（**プロキシ**）を通ってから API に届きます。設定しないと、全員の IP が「中継サーバーの IP」に見えてしまい、**全員まとめて 10 回**で止まってしまいます。`1` は「1つ手前の中継サーバーが教えてくれる IP を信じる」という意味です。

## 設計のポイント（面接で話せること）

- **使い捨てのゲストにした理由**：共有アカウントだと、前の人の操作が次の人に見えてしまう。人ごとに分けて、いつでもきれいな状態で見せられるようにした
- **ゲストをどう消すか**：無料プランでは定期実行が使えないので、ゲストを作るタイミングで古いゲストを消した。ノートは CASCADE で一緒に消える
- **本物のユーザーを守る**：消す対象を `isGuest` の列ではっきり分けた。メールアドレスの形で見分けるより安全
- **悪用への対策**：回数の制限を入れた
- **フロントの処理を共通にした**：ゲストもログインも `{ user, token }` を返すので、ログイン後の処理を1つにまとめられた
