# ドラッグの E2E（段階 2 の課題）

> **段階 2 の進め方**：AI もヒントも使わずに、**時間を計って**書きます。目的は「白紙から書けるか」と「どこで止まるか」を知ることです。止まった場所は、失敗ではなく**弱点リストの材料**です。

---

## ルール

| 項目 | 内容 |
| --- | --- |
| 制限時間 | **40 分**（平日 1 回分）。始めた時刻と終えた時刻をメモする |
| 見てよいもの | このリポジトリのコード（`e2e/` の既存のテスト・`mock-api.ts` など）、Playwright と dnd-kit の公式ドキュメント |
| 見ないもの | AI（Claude・Copilot の補完も切る）、下の「封をしたヒント」 |
| 1 か所で 10 分止まったら | どこで、何がわからなかったかをメモしてから、封をしたヒントを **1 段だけ**開いてよい |
| 時間が来たら | 途中でも止める。そこまでのコードとメモを見せる |

---

## 準備

1. Sourcetree で `master` に切り替えてプル
2. `test/drag-e2e` というブランチを作る

---

## ゴール

`e2e/drag.e2e.ts` を作り、次のテストを書く。

### 必須：並び替えが画面と API に反映される

| 項目 | 内容 |
| --- | --- |
| 準備 | ノートを 3 つ（「ノート 1」「ノート 2」「ノート 3」）持った状態でログインする |
| 操作 | 「ノート 3」を、「ノート 1」の上に**ドラッグ**する |
| 確かめること ① | サイドバーの並びが「ノート 3 → ノート 1 → ノート 2」になる |
| 確かめること ② | API に、新しい並び順（`[3, 1, 2]`）が送られる |

### 余裕があれば：失敗したら元に戻る

| 項目 | 内容 |
| --- | --- |
| 準備 | 並び替えの API だけが失敗する（500 を返す）ようにする |
| 操作 | 同じようにドラッグする |
| 確かめること | 並びが「ノート 1 → ノート 2 → ノート 3」に戻る |

> 「小さな修正」で書いた、楽観的更新の巻き戻し（`preOrderedNotes` に戻す）を、画面から確かめるテストです。

## 封をしたヒント（10 分止まったときだけ、1 段ずつ）

<details>
<summary>ヒント A：ドラッグの操作がうまくいかない</summary>

#### A-1（何を）

このアプリのドラッグには、「何 px 動かしたら始まるか」の決まりがあります。`src/components/NoteList/index.tsx` の `sensors` を見てください。Playwright の操作が、その決まりを満たしているか考えてみてください。

<details>
<summary>A-2（使うもの）</summary>

`locator.dragTo()` は、一瞬で移動するので、dnd-kit が「ドラッグが始まった」と気づけないことがあります。`page.mouse` の `move`・`down`・`up` を使うと、少しずつ動かせます。キーボード（つまみにフォーカス → Space → 矢印 → Space）で動かす方法もあります。

</details>
</details>

<details>
<summary>ヒント B：つまみ（⋮⋮）の探し方がわからない</summary>

#### B-1（何を）

つまみには、画面に見えない名前が付いています。`src/components/NoteList/SortableNoteItem.tsx` を見てください。

<details>
<summary>B-2（使うもの）</summary>

つまみは 3 つあるので、「どのノートのつまみか」を絞り込む必要があります。行（ノートのタイトルを含む要素）で絞ってから、その中のつまみを探す、という順番で考えてみてください。

</details>
</details>

<details>
<summary>ヒント C：並び順の確かめ方がわからない</summary>

#### C-1（何を）

「ノート 3 が見える」だけでは、順番は確かめられません。サイドバーのノートのタイトルを、**上から順に全部**取り出して比べる方法を考えてください。

<details>
<summary>C-2（使うもの）</summary>

Playwright の locator には、当てはまる要素の文字を、配列でまとめて確かめる `expect(locator).toHaveText([...])` があります。

</details>
</details>

<details>
<summary>ヒント D：API に送られた中身の確かめ方がわからない</summary>

#### D-1（何を）

`mock-api.ts` で、並び替えのリクエストをどう受け取っているかを見てください。送られた中身を読む方法が書いてあります。

<details>
<summary>D-2（使うもの）</summary>

テストの中で「このリクエストが来るのを待つ」には `page.waitForRequest()` を使います。待ち始めるのは、ドラッグの**前**です（あとから待つと、もう来てしまっていることがあります）。

</details>
</details>

<details>
<summary>ヒント E（余裕があれば用）：並び替えだけ失敗させたい</summary>

#### E-1（何を）

`page.route` は、**あとから登録したほうが先に**リクエストを受け止めます。`mockApi(page, …)` のあとに、並び替えの URL だけを受け止める `page.route` を足すことを考えてみてください。

</details>

## ふり返り（1 回目・2026-11-24）

| 項目 | 結果 |
| --- | --- |
| かかった時間 | 約 60 分（ルールを緩めて、書き方は AI に調べてよいことにした） |
| 必須 | ○（画面の並び ＋ API に送った中身。3 回続けて通る） |
| 余裕があれば | 未着手 |
| 開いたヒント | A〜D すべて。`waitForRequest` の形は答えを見た |

### 弱点リスト

| # | 弱点 | どこで出たか | 次にやること |
| --- | --- | --- | --- |
| 1 | **初めて使う API の書き方**（Playwright の `page.mouse`、`waitForRequest`） | 並び替えの操作で 20 分 | 新しい書き方は、課題の**前に講義**で押さえる |
| 2 | **セレクタ**（CSS のクラスの書き方、共通の部品のクラスとの区別） | `locator("note-drag-handle")`、`.note-item`、`.sidebar-item` で 3 回 | 探す前に、対象の部品の `return` を読んで、**その部品にしかない**目印を見つける |
| 3 | **Promise を先に作って、あとで `await` する形** | `waitForRequest` | `StartupScreen` のタイマーと同じ種類の考え方。講義の練習問題に入れる |
| 4 | **待つ確認と、その場の確認の区別**（`await expect(locator)` と `expect(値)`） | `await` の付け忘れ、`allTextContents` | `docs/playwright-cheatsheet.md` の 7 章 |
| 5 | **調べた例を、自分の課題に合わせて読みかえる** | ドラッグの向きが、例のまま逆だった | 例を使う前に「この例は、何を、どこからどこへ動かしているか」を 1 行で書いてから使う |

### 次の段階 2 の課題の形

- 新しい書き方が必要なら、**先に講義**（`docs/〜-lecture.md`）
- 課題は「講義で習った書き方を、白紙から組み立てる」ものにする
- 書き方を AI に調べてもよい。ただし、何を聞いて、どう直して使ったかをメモする
