# ドラッグ＆ドロップ（並び替え）手順書

サイドバーのノートを、ドラッグして好きな順番に並び替えられるようにします。

## ゴール

```
買い物メモ        ┐ ドラッグして
読書記録          │ 入れ替える
旅行の計画   ←────┘
```

- サイドバーのノートをつかんで、上下に動かせる
- 離した位置に並び替わる
- **ページを再読み込みしても、並び順が残る**（DB に保存する）

---

## 決めること：どこまでやるか

| 範囲 | できること | 難しさ |
| --- | --- | --- |
| **A. 同じ階層の中で並び替え** ← おすすめ | 「買い物メモ」と「読書記録」の順番を入れ替える。子ノートの中でも同じことができる | 中 |
| B. 別の親の下に移動 | 「読書記録」を「買い物メモ」の子にする | 大（どこに落としたら「子にする」なのか、の判定が必要。子孫を自分の下に入れてしまう事故も防ぐ必要がある） |

→ **A で始めて、動いたら B を考える**のがおすすめです。A だけでも「並び替えのロジック」「DB の設計」「楽観的更新」と、学べることは十分あります。

### 青い線（core だけ）か、すき間（sortable）か

本家は青い線ですが、比べたうえで **sortable（すき間）** にしました。

| | `@dnd-kit/core` だけ（青い線） | `@dnd-kit/sortable` も使う（すき間）← 採用 |
| --- | --- | --- |
| 動かしている間 | 線の見た目を自分で作る | ほかの行が自動でずれて、すき間ができる |
| 前か後ろかの判定 | 自分で書く | いらない |
| 並び替えの関数 | `(notes, activeId, overId, place)` | `(notes, activeId, overId)` |
| あとで範囲 B（子にする） | 判定を足すだけ | 作り直しが多い |

- `@dnd-kit/sortable` は `@dnd-kit/core` の上に作られた「並び替え用のセット」。core も一緒に使う
- 開いているノートの子は、`NoteList` の `<div key={note.id}>` に行と子の一覧が入っているので、その `div` を動かせば一緒についてくる
- `NoteList` の階層ごとに `SortableContext` で囲む。ただし違う親の行の上で離すこともできるので、「同じ親か」は自分で確かめる
- sortable には `arrayMove`（配列の要素を動かす関数）がついているが、**使わずに `reorderNotes` を自分で書く**（学習のため）

## 今の仕組みを観察する（大事な発見）

### 並び順は、今どう決まっているか

1. API（`note.controller.ts`）は、ノートを **作った日時の新しい順**（`order: { createdAt: 'DESC' }`）で返している
2. ところがフロントは、受け取ったノートを `mergeNotes` で混ぜている
3. `mergeNotes` は `{ [id]: note }` というオブジェクトを作って `Object.values` で配列に戻す
4. **JavaScript のオブジェクトは、数字のキーを小さい順に並べる**ので、ここで **id の小さい順（＝古い順）** に並び直ってしまう

つまり、**API が決めた順番は、今は画面に届いていません**。サイドバーは、たまたま「id の小さい順」で表示されています（Vitest のときに「ちょっとした発見があります」と書いたのが、これです）。

### ここから分かること

- 並び順を **DB に「番号」として保存**する必要がある（今は順番の情報がどこにもない）
- フロントでは、**表示する直前に、その番号で並べ替える**必要がある（`mergeNotes` に順番を任せない）

**たとえ**：Shopify のコレクションの「手動で並び替え」と同じです。商品に「並び順の番号」を持たせて、表示のときにその番号で並べています。WordPress の `menu_order` も同じ考え方です。

## 全体の設計

### ① DB：ノートに `position`（並び順の番号）を持たせる

| id | title | parentId | position |
| --- | --- | --- | --- |
| 1 | 買い物メモ | null | 0 |
| 2 | 読書記録 | null | 1 |
| 3 | 旅行の計画 | null | 2 |
| 4 | 本のリスト | 2 | 0 |

- `position` は **同じ親の中での順番**（0, 1, 2 …）。親が違えば、また 0 から数える
- 今あるノートには、マイグレーションで **作った順に番号を振る**（並び順が急に変わらないように）

### ② API：並び順を返す・保存する

| 変更 | 中身 |
| --- | --- |
| 一覧（`GET /notes`） | `position` の小さい順で返す |
| 作成（`POST /notes`） | 新しいノートは、同じ親の中で**一番下**（今ある最大＋1） |
| **並び替え（新規）** `PATCH /notes/reorder` | 並び替えたあとの id の順番 `{ ids: [3, 1, 2] }` を受け取って、その順に `position` を 0, 1, 2 … と振り直す |

**なぜ「id の順番を全部送る」のか**：「3 を 1 の上に動かした」だけを送るやり方もありますが、サーバー側で計算が必要になり、ずれたときに直しにくくなります。**並び替えたあとの完成形をそのまま送る**ほうが、シンプルで間違いにくいです。1つの階層のノートは多くても数十件なので、全部送っても問題ありません。

### ③ フロント：ドラッグして、並び替えて、保存する

```
① ノートをつかんで、別のノートの上で離す
② dnd-kit が「何を（active）」「どこに（over）」動かしたか教えてくれる
③ 並び替えの関数で、新しい順番を計算する          ← 純粋な関数（Vitest でテスト）
④ すぐに画面を並び替える（store を更新）           ← 楽観的更新
⑤ API に新しい順番を送る（PATCH /notes/reorder）
⑥ 失敗したら、元の順番に戻して alert
```

**楽観的更新（optimistic update）とは**：API の返事を待たずに、「たぶん成功する」と考えて先に画面を変えるやり方です。ドラッグして離したのに、返事が来るまで元の位置に戻っていたら気持ち悪いので、先に動かします。失敗したときだけ元に戻します。

**たとえ**：EC サイトで「カートに追加」を押したら、通信の完了を待たずにカートの数字を +1 して、失敗したら戻すのと同じです。

### ライブラリ：dnd-kit

| 方法 | よいところ | 気になるところ |
| --- | --- | --- |
| **@dnd-kit/core + @dnd-kit/sortable** ← 採用 | React 用の定番。並び替え（sortable）の部品がそろっている。キーボード操作にも対応 | 覚えることが少しある |
| HTML の Drag and Drop API（`draggable` 属性） | ライブラリなし。JS の知識で書ける | スマホで動かない。並び替えのアニメーションや判定を全部自分で書く必要がある |
| react-beautiful-dnd | 昔の定番 | 開発が終了している |
| @dnd-kit/react | dnd-kit の新しい版 | まだ 0.x（正式版の前）で、書き方が変わる可能性がある |

#### ① マイグレーション：列を足して、番号を振る

```sql
-- 1. 列を足す（今あるノートは、いったん全部 0）
ALTER TABLE "notes" ADD "position" integer NOT NULL DEFAULT 0

-- 2. 持ち主ごと・親ごとに、id の小さい順に 0, 1, 2 … と振る
UPDATE "notes" AS n
SET "position" = numbered.rn - 1
FROM (
  SELECT "id", ROW_NUMBER() OVER (PARTITION BY "userId", "parentId" ORDER BY "id") AS rn
  FROM "notes"
) AS numbered
WHERE n."id" = numbered."id"
```

- **`ROW_NUMBER()`**：上から 1, 2, 3 … と番号を付ける SQL の関数。1から始まるので、`- 1` で 0 始まりにしている
- **`PARTITION BY "userId", "parentId"`**：「持ち主と親が同じもの」ごとにグループを分けて、**グループごとに 1 から数え直す**。PHP でいえば、`foreach` の中でグループが変わったらカウンターを 0 に戻すイメージです
- **`ORDER BY "id"`**：今のサイドバーは id の小さい順に見えているので（上の「大事な発見」）、その順番を保つ。デプロイしても、並び順が急に変わらない

#### ② 一覧：position の順に返す

```ts
order: { position: 'ASC', id: 'ASC' },
```

`position` が同じとき（例：まだ番号が振られていない 0 同士）は、id の小さい順にする。並び順が毎回ぶれないようにするためです。

#### ③ 作成：同じ親の中で一番下に置く

```ts
SELECT MAX(position) … WHERE userId = 自分 AND parentId = 同じ親
position = (最大値 ?? -1) + 1
```

まだ1件もないときは `MAX` が `null` になるので、`-1` として扱って 0 番にしています。

#### ④ 並び替え：`PATCH /notes/reorder`

```
送るもの：{ "ids": [9, 7, 8] }   ← 並び替えたあとの順番
返すもの：{ "notes": [...] }     ← position を振り直したノート（新しい順番）
```

処理の流れ：

1. `ids` が「数字の配列・空でない・重複なし」か確かめる → だめなら **400**
2. 全部が自分のノートか確かめる → 足りなければ **404**（他人のノートは並び替えられない）
3. 全部が同じ親の下か確かめる → 違えば **400**（今回は A：同じ階層の中だけ）
4. **トランザクション**で、`ids` の順に `position` を 0, 1, 2 … に更新
5. 更新後のノートを返す

**トランザクションとは**：複数の更新を「全部成功」か「全部なかったことにする」のどちらかにする仕組みです。途中で失敗して「半分だけ並び替わった」状態を防ぎます。**たとえ**：EC の注文で「在庫を減らす」と「注文を作る」は、片方だけ成功すると困るので、まとめて1つにしますよね。それと同じです。

**`'/reorder'` を `'/:id'` より前に書く理由**：Express は上から順にルートを見ます。`PATCH /:id` が先にあると、`/reorder` の `reorder` が `:id` として扱われてしまいます。

| 取り出す**前** ← 正しい | 3, 1, 2 ✅ | 2, 3, 1 ✅ |
| 取り出した**あと** | 3, 1, 2 ✅ | 2, 1, 3 ❌ |

上へ動かすときは、たまたまどちらでも同じ結果になる。なので、テストには #1 と #2 の**両方**を入れる。

#### わかったこと：`splice`

`splice` は「消す」と「消したものを返す」を同時にやる。元の配列そのものを書き換えるので、**必ずコピーに対して使う**。

```ts
const movedNote = updatedNotes.splice(activeIndex, 1)[0]; // ① 抜き出して手に持つ
updatedNotes.splice(overIndex, 0, movedNote);             // ② 手に持ったものを差し込む
```

| 書き方 | 引数の意味 | 戻り値 |
| --- | --- | --- |
| `splice(activeIndex, 1)` | activeIndex 番目から 1 個消す | 消したものの**配列** `[note3]` → `[0]` で中身を取り出す |
| `splice(overIndex, 0, movedNote)` | overIndex 番目から 0 個消して、movedNote を入れる | `[]`（何も消していないので使わない） |

#1（3 → 1）の場合：

| 行 | `updatedNotes` | `movedNote`（手に持っているもの） |
| --- | --- | --- |
| 始め | [1, 2, 3] | — |
| ① のあと | [1, 2] | 3 |
| ② のあと | [3, 1, 2] | 3 |

- **`[0]` が必要な理由**：`splice` は何個でも取り出せるので、1 個でも配列で返す。`[0]` がないと、配列の中に配列が入る（`[[note3], note1, note2]`）
- 同じ意味の書き方：`const [movedNote] = updatedNotes.splice(activeIndex, 1);`（分割代入。`useState` と同じ形）
- **たとえ**：本棚の1冊を抜き出して手に持ち、入れたい場所のすき間に差し込む。PHP の `array_splice` と同じ動き

#### id はどこから来るか（Step 3 の予告）

番号（インデックス）は dnd-kit からはもらえないが、**id はもらえる**。だから `reorderNotes` は id を受け取って、中で番号を調べる。

```ts
onDragEnd(event) {
  event.active.id  // 動かしたノートの id
  event.over?.id   // 落とした先のノートの id（どこにも落とさなければ over は null）
}
```

- 各行に `useSortable({ id: note.id })` で id を登録しておくので届く（HTML の `data-id` 属性のイメージ）
- `reorderNotes` は dnd-kit のことを知らなくてよい。テストでは `reorderNotes(notes, 3, 1)` と数字を渡すだけ

| --- | --- |

| 5px 動かしたらドラッグ開始（`distance: 5`） | つまみをちょっと触っただけでは始まらない |
