# E2E テスト（Playwright）手順書

testing-ci-guide.md の **Step 4** の詳しい版です。

## E2E テストとは

**ロボットが本物のブラウザを開いて、人と同じようにクリック・入力して、画面が正しいか確かめる**テストです。

| | ユニットテスト（Vitest） | E2E テスト（Playwright） |
| --- | --- | --- |
| 確かめる単位 | 関数1つ | 画面の操作の流れ（ログイン → ノートを作る…） |
| 動かすもの | 関数だけ | ブラウザ＋アプリ全体 |
| 速さ | 一瞬（13件で 0.1 秒） | 1件で数秒 |
| 見つけられるバグ | 計算の間違い | 「ボタンが押せない」「画面がつながっていない」 |
| たとえ | 電卓のボタンを1つずつ確かめる | お客さんになりきって、商品を選んで購入まで進んでみる |

E2E は遅くて壊れやすいので、**大事な流れを 1〜3 本だけ**書くのがふつうです。

---

## 決めること：API をどうするか

このアプリは、画面（Vercel）と API（Render）と DB（Neon）の3つでできています。E2E で画面を動かすと、画面は API を呼びます。**その API をどこに向けるか**で、3つのやり方があります。

### A. API を「ニセモノ」に差し替える（おすすめ）

Playwright には、**ブラウザが出すリクエストを途中で受け止めて、用意した答えを返す**機能（`page.route`）があります。

```
ブラウザ ──GET /notes──→ ✋ Playwright が受け止める
        ←── 用意しておいた [{ id: 1, title: "テスト" }] を返す
```

- ✅ API も DB も起動しなくていい → **CI でそのまま動く**
- ✅ 毎回同じデータ → 結果がブレない
- ✅ 本番のデータに一切触らない
- ❌ API の中身が正しいかは確かめられない（画面側だけのテスト）

**たとえ**：Shopify のテーマを作るときに、本物の商品データではなく、ダミーの商品データで見た目と動きを確かめるのと同じです。

### B. 手元で API と DB も起動して、本物に向ける

- ✅ 画面から DB まで、本当に全部つながっているか確かめられる
- ❌ CI で動かすには、API のリポジトリも取ってきて、Postgres も CI の中で起動する必要がある（設定がかなり複雑）
- ❌ テストのたびにデータが増えるので、片付けが必要

### C. 本番のサイトに向ける

- ❌ **本番の DB にテスト用のノートが作られる**。おすすめしません

### おすすめ：A で始める

- 今の目的（ポートフォリオで「CI で E2E が動いている」を見せる）には A で十分です
- API 側は、別のやり方（API のテスト）で守るのが実務でも一般的です
- B は、A に慣れてから「手元だけで動かす」形で追加できます

### テストの実行のしかた

```bash
npm run test:e2e
```

- 自動でアプリ（5174 番）が立ち上がり、見えないブラウザでテストが動きます。いつもの `npm run dev`（5173 番）を起動したままでも大丈夫です
- **ブラウザの動きを目で見たいとき**：`npx playwright test --ui`（操作を1ステップずつ再生できる画面が開きます）
- 失敗したとき：`npx playwright show-report` で、スクリーンショットや操作の記録を見られます

### 全体の流れ

```
① Playwright が Vite の開発サーバーを起動（VITE_API_URL を http://localhost:9999 にして）
② テストが始まる：mockApi() で「localhost:9999 へのリクエストは全部受け止める」と登録
③ ブラウザで /signin を開く → 入力 → ログインボタン
④ アプリが POST localhost:9999/auth/signin を投げる
   → ✋ mockApi が受け止めて、{ user, token } を返す
⑤ アプリが GET /notes・/notes/favorites を投げる
   → ✋ mockApi が、用意したノート2つを返す
⑥ サイドバーにタイトルが出たか、URL が / になったかを確かめる
```

**ポイント**：アプリのコードは**1行も変えていません**。アプリは、いつもどおり API を呼んでいるつもりで動いています。`localhost:9999` には本当は何もありませんが、届く前に Playwright が返事をしています。

### playwright.config.ts の要点

| 設定 | 意味 |
| --- | --- |
| `testMatch: "**/*.e2e.ts"` | E2E のファイル名は `〇〇.e2e.ts`。Vitest（`〇〇.test.ts`）と混ざらないようにするため |
| `webServer` | テストの前に `npm run dev -- --port 5174` を自動で起動する |
| `webServer.env.VITE_API_URL` | `.env` より優先される。アプリが API を投げる先を、ニセモノの住所に変える |
| `retries` | CI では、失敗したら1回だけやり直す（E2E はたまたま失敗することがあるため） |
| `trace: "retain-on-failure"` | 失敗したときだけ、操作の記録を残す |

### テストの読み方（signin.e2e.ts）

```ts
test("ログインすると、サイドバーに自分のノートが表示される", async ({ page }) => {
  await mockApi(page, { notes: [createMockNote(1, "買い物メモ"), …] });
  await page.goto("/signin");
  await page.getByLabel("メールアドレス").fill("test@example.com");
  await page.getByRole("button", { name: "ログイン" }).click();
  await expect(page.getByText("買い物メモ")).toBeVisible();
});
```

- **`test`**：Vitest の `it` と同じ役割（1つのテスト）
- **`page`**：ブラウザの1つのタブ。これを操作します
- **`await`**：ブラウザの操作は時間がかかるので、1つ終わるのを待ってから次に進みます
- **要素の探し方**：CSS のクラス名ではなく、**人が見て分かるもの**で探します
  - `getByLabel("メールアドレス")`：`<label>` の文字で入力欄を探す（`htmlFor` と `id` がつながっているから使える）
  - `getByRole("button", { name: "ログイン" })`：「ログイン」と書かれたボタン
  - `getByText("買い物メモ")`：その文字が出ている場所
- **`expect(…).toBeVisible()`**：画面に見えているか。**見えるまで最大5秒待ってくれる**ので、API の返事を待つ処理を自分で書かなくていい

**なぜクラス名で探さないのか**：`.sidebar-item-label` のようなクラス名は、デザインを変えると変わります。「ログインボタン」は、見た目が変わっても「ログインボタン」のままです。**ユーザーと同じ目線で探す**と、壊れにくいテストになります。

### mock-api.ts の要点

- `page.route("http://localhost:9999/**", …)`：その住所へのリクエストを全部受け止める
- メソッド（GET・POST）とパス（`/auth/signin` など）を見て、返す答えを選ぶ
- `route.fulfill({ json: … })`：用意した JSON を返す
- 用意していないリクエストは **404** を返し、ターミナルに `[mockApi] 未対応のリクエスト` と出す → 2本目を書くときに「何を足せばいいか」が分かる

## 2本目：あなたが書く（ノートを作る）

### 流れ

ログイン済みの状態から、サイドバーの「＋」（ノートを作るボタン）を押す → サイドバーに新しいノートが増えて、詳細画面（`/notes/〇〇`）に移る。

### 進め方

1. まず、**本物のアプリで操作を観察**する（いつもの「観察」と同じ）
   - どのボタンを押す？　そのボタンには何と書いてある？（`getByRole` で探せる名前があるか）
   - 押したら、API に何が飛ぶ？（開発者ツールの Network タブで、メソッドとパスを見る）
   - そのあと画面はどう変わる？
2. **mock-api.ts に、足りない API を足す**（ヒント：ノートを作る API）
   - 作ったノートを返す必要があります。どんな JSON を返せばいいかは、Network タブの「Response」で本物の返事を見ると分かります
3. `e2e/create-note.e2e.ts` を作って、テストを書く
   - ログインの部分は1本目と同じです。何度も書くのが大変なら、「ログイン済みにする」方法もあります（ヒントが欲しくなったら聞いてください）
4. `npx playwright test --ui` で、動きを見ながら直す

### mock-api.ts に足したもの（AI・2026-11-14）

本物の API（`notion-clone-api-postgres/src/modules/notes/note.controller.ts`）と同じ形・同じステータスにしています。

| リクエスト | 返すもの | 本物との対応 |
| --- | --- | --- |
| `POST /notes` | 作ったノートを**包まずに**そのまま、**201** | `res.status(201).json(note)` |
| `GET /notes/:id` | そのノートを包まずに（200）。なければ 404 | `res.status(200).json(note)` / 404 |

- **id の決め方**：今あるノートの一番大きい id ＋1（`Math.max(0, ...ids) + 1`。ノートが0件でも 1 になるように `0` を入れている）
- **作ったノートは `notes` に足す**：そのあとの `GET /notes`（サイドバー）や `GET /notes/:id`（詳細画面）でも返せる。本物の DB と同じ動きになる
- **`notes` はコピーしてから使う**：テストから渡された配列を書き換えないため
- **`/notes/15` の見分け方**：正規表現 `^\/notes\/(\d+)$`。「`/notes/` のあとに数字だけ」なので、`/notes/favorites` には当てはまらない
- `createMockNote` の `title` を `string | null` にした：作った直後のノートは本物でも `title: null` のため

### ハマりどころ：見た目が同じでも、違う文字のことがある

「ド」「バ」のような濁点つきの文字は、コンピューターの中で2通りの書き方があります。

- **NFC**：「ド」で1文字（ふつうはこちら）
- **NFD**：「ト」＋「゛」の2文字（Mac の Finder でファイル名を扱ったときなどに混ざることがある）

画面では同じに見えますが、Playwright は別の文字として扱うので、`getByLabel("メールアドレス")` が見つからなくなります。VS Code で該当の文字を打ち直すと直ります。

### ヒント

- ボタンに文字がない（アイコンだけ）の場合、`getByRole` で探せないことがあります。そのときは、どう探すとよいか相談してください（アプリ側に `aria-label` を足す方法があります。これはアクセシビリティの改善にもなります）
- テストが「未対応のリクエスト」で止まったら、ターミナルのログを見て、mock-api.ts に足していきます
